🟡 中危 问题1 — 日报接口在内存中分页且未限制日期跨度
文件：backend/app/routers/reports.py　位置：约第 120 行
问题描述：list_daily_output_report 先按 date_from/date_to 取出全部记录构建 items，再在 Python 侧切片分页；date_from/date_to 来自查询参数且无最大跨度校验，一次请求可拉取任意长区间（如数年）的全部工单/产出记录，造成内存与响应时间无界增长（Big-O 随区间线性、无上限）。建议：在查询层用 SQL LIMIT/OFFSET 分页并返回 total；同时对 (date_to - date_from) 设上限（如 92 天）超出返回 400，或在 schema 中用校验器约束。

🟡 中危 问题2 — 产线设备映射为全表加载 + 嵌套循环
文件：backend/app/routers/reports.py　位置：约第 150 行
问题描述：_build_daily_output_line_device_map 一次性把 Equipment 全表读入内存，然后对每条 line 遍历全部 equipment 做匹配，复杂度 O(lines × equipment)，设备量大时每次请求都全表扫描并产生大量无谓比较。修复：先在数据库侧按 location 前缀/关联字段过滤（如 Equipment.location.startswith 或 join ProductionLine），或一次性构建 location 索引（dict/前缀集合）后 O(1) 查找，避免嵌套循环与全表加载。
